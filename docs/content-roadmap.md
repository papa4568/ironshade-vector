## Execution contract

- Execute top to bottom. The **first unchecked top-level item is next** unless the user explicitly changes priority.
- One checkbox should fit one realistic **implement → test → build → APK verification** cycle.
- Split an item before coding if it spans independent systems or verification cycles; combine tiny changes when they touch the same system and can be verified together.
- An item is complete only when its requested behavior works, relevant regression checks pass, the production build succeeds, and the Android deliverable is verified as required by the repository workflow.
- After verified completion, move the completion detail/evidence to the archive and remove the item from this file.
- If repository evidence shows an active item is already complete, verify that evidence before archiving it. If only part is complete, rewrite the item around the remaining work.

- [ ] **P20-A — Repair effective non-combat Interface Size scaling** — The first P20-A implementation persists Compact / Default / Large and changes the root font size, but representative management UI still remains effectively unchanged because major Armory/menu/layout rules are hard-coded in pixels and bypass the root-rem scale. Replace the false-positive root-only behavior with an interface-size system that produces real, visible size/reflow changes across supported non-combat surfaces by routing typography, spacing, control chrome, panel/card geometry, icons, and informational HUD chrome through shared scalable tokens or equivalent layout-aware variables. Audit the pixel-heavy Armory/Settings and shared management styles (including `menuOverhaul.css`, `part3.css`, `classBuilds.css`, and compact P19 overrides) so Compact fits materially more UI, Default preserves the current baseline, and Large materially enlarges supported UI without using CSS transform/browser-zoom tricks that break layout or safe areas. Keep Interface Text Size independently composable. Continue to exclude movement, FIRE, DODGE, class skills, ACT, and all combat-control hit regions from general Interface Size. **Done when:** Compact, Default, and Large produce measurable ordered differences on actual rendered elements—not just `:root` font size—including Build tabs, Settings rows/selects, representative Loadout/Progression/Skills/Crafting panels, at least one Ship/Command management surface, and informational HUD chrome; automated checks compare real DOM rectangles/computed font/padding/spacing values and would fail the current `9ee1981` implementation; desktop and compact-landscape visual/runtime QA show the three modes are obviously distinguishable with no clipping/horizontal overflow or broken safe-area behavior; saved profiles restore the selected size; combat-control geometry remains bit-for-bit invariant across Interface Size values; Browser E2E + production build pass; and the verified APK reproduces the visible scaling on-device.

- [ ] **P20-C — Class skill and skill-modifying gear behavior audit** — Audit the complete runtime path for all nine class skills (Vanguard, Vector, Systems), their shared Lenses/class Evolutions, class mechanic state, specialization/capstone interactions, class-skill-family tuning, and every ordinary affix/Singular rule that modifies a skill or skill-family behavior. Gear may modify the active class kit but must not reintroduce per-item skill ownership or off-class weapon behavior. **Done when:** regression coverage exercises each class's three base skills for targeting/resource/cooldown/core effect and signature mechanic, verifies power/range/control/armor/recovery/cost composition, covers every registry-declared skill-affecting affix and Singular skill transformer against its advertised rule/tradeoff, catches stale neutral MAG/MARK/ARC wording or behavior where class-specific skills are active, production build passes, and APK combat smoke confirms the three class kits and representative skill-modifying gear.

- [ ] **P20-D — Class-aware recommended build paths** — Add or reconcile a small authored set of recommended Operator Network paths using the verified P20-C mechanics and the existing planner instead of a generic optimizer. Recommendations must respect the locked class arsenals and explain the gameplay loop they strengthen: Vanguard recommendations should connect Breacher pressure/armor break/Guard, Vector recommendations should connect Rail precision/range/mobility/Slipstream, and Systems recommendations should connect Carbine capacitor/control/recovery/Closed Loop; selected specializations may refine those paths only when their milestones/unlocks apply. - [ ] **P20-E — Distinct gameplay identities for standard repeatable contracts** — Rework the standard non-story repeatable contract families so Salvage, Boarding, and Stabilization are recognizable mission types rather than interchangeable combinations of the shared objective pool. Build each family from reusable encounter/objective primitives but give it an authored primary loop, objective sequencing, encounter/director pressure, environmental fit, and safe-vs-deep risk pattern that remains identifiable while locations/conditions rotate. Preserve campaign/story contracts and the already-distinct Daily Operation, Escalation, Directive, and rare megastructure systems instead of flattening them into the new standard templates. **Done when:** deterministic multi-cycle generation shows all three standard families repeatedly produce legal but materially different mission flows, encounter/objective tests verify each family's authored mechanics and deep-risk identity, campaign/special-operation regressions remain unchanged, Browser E2E can distinguish the three choices from briefing/objective presentation before deployment, production build passes, and Android play smoke completes one representative contract of each family.

- [ ] **P20-F — Individual incentives for repeatable contract choices** — Give each standard repeatable contract family a clear pre-deployment reason to run it by differentiating its reward/chase profile using the existing economy, faction/reputation, gear-source, optional-objective, and recovery systems rather than adding redundant currencies by default. Surface the distinctive payoff on the contract card/briefing, keep safe/deep extraction tradeoffs meaningful, and tune the profiles so no single family is the strictly best answer for every progression need while each remains useful across repeated cycles. **Done when:** settlement/generation tests prove each family grants its authored incentive and cannot leak campaign-only rewards, a balance matrix across representative early/mid/late profiles shows distinct needs served by each family, UI clearly communicates the expected payoff before launch, Browser E2E + production build pass, and the verified APK confirms reward presentation and post-contract settlement for all three families.
