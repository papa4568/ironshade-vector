# Ironshade Vector — Active Production Roadmap

Only active/future executable work lives here. Completed and verified work belongs in [content-roadmap-archive.md](./content-roadmap-archive.md). Stable product rules live in [product-constraints.md](./product-constraints.md).

## Execution contract

- Execute top to bottom. The **first unchecked top-level item is next** unless the user explicitly changes priority.
- One checkbox should fit one realistic **implement → test → build → APK verification** cycle.
- Split an item before coding if it spans independent systems or verification cycles; combine tiny changes when they touch the same system and can be verified together.
- An item is complete only when its requested behavior works, relevant regression checks pass, the production build succeeds, and the Android deliverable is verified as required by the repository workflow.
- After verified completion, move the completion detail/evidence to the archive and remove the item from this file.
- If repository evidence shows an active item is already complete, verify that evidence before archiving it. If only part is complete, rewrite the item around the remaining work.

## P18 — Beta Combat Reliability & UI Clarity

- [x] **P18-B — Attack Speed owns tracking + firing cadence** — Introduce one canonical Attack Speed multiplier in the shared combat-build/stat pipeline instead of deriving tracking speed from aim-assist mode or unrelated projectile/reload stats. Apply that same multiplier to weapon fire rate and assisted target turn/convergence rate, add an attainable authored stat source through the existing Gear/Operator Network stat registries without creating a parallel progression system, and surface the stat in plain language where build changes are shown. Light/Balanced assist may still change target-selection behavior, but not tracking turn speed. **Done when:** raising Attack Speed measurably increases both shots-per-second and lock-on rotation speed by the same derived multiplier, baseline cadence remains unchanged at 1.0x, no other setting/stat speeds up tracking, save migration remains compatible, balance/gameplay/gear-network regressions pass, the production build succeeds, and the Android debug APK passes a touch/controller targeting smoke check.

- [x] **P18-C — Persist planned progression paths** — Move Operator Network planner targets out of transient Armory component state and into normalized persisted progression state, with a schema-safe migration from existing Network saves. Preserve the planner's non-destructive contract: planned targets may survive closing/reopening Build and a full app restart, but planning must never spend points or silently allocate nodes; invalid, removed, incompatible, or already-satisfied targets should normalize safely. **Done when:** a multi-node planned route reappears after closing/reopening Progression and after save/reload, legacy saves migrate without losing allocations or points, stale plan targets are pruned deterministically, planner/search/allocation behavior is unchanged otherwise, save/operator-network regressions pass, the production build succeeds, and the Android debug APK verifies persistence across an app relaunch.

- [x] **P18-D — Shared progressive-disclosure + requirement-state UI primitives** — Implement the new design-system clarity rules with one reusable accessible popup/sheet pattern for secondary explanations and one shared eligibility presentation for interactive actions (ready / active / blocked plus plain-language reason and next requirement). Reuse the existing panel/focus/safe-area tokens, preserve keyboard/controller/touch dismissal and focus behavior, and keep costs, tradeoffs, warnings, and blockers visible at the decision point rather than hiding essential information in a popup. **Done when:** changed management screens can use the same popup and requirement-state primitives instead of bespoke shells or disabled-only cues, reduced-motion/high-contrast/text-scale/mobile behavior remains intact, focused UI regressions pass, the production build succeeds, and the Android debug APK passes portrait/landscape touch and back-navigation smoke checks.

- [x] **P18-F — Progression, Skills + Crafting action clarity pass** — Apply the shared clarity primitives across the remaining Build management surfaces that currently mix dense instructional copy with disabled actions. Convert common blockers into direct next-step language (for example: required level, missing progression points, prerequisite/adjacent route, exclusive Keystone choice, class-family ownership, Microforge tier, socket capacity, or missing salvage), collapse secondary “how this system works” explanations and technical math into on-demand help where appropriate, and keep immediate outcomes/costs/tradeoffs beside the action. **Done when:** users can distinguish what is available now, what is selected/active, and exactly why an unavailable action is blocked across Progression, Skills, and Crafting without decoding generic LOCKED/disabled states; critical information remains visible without opening help; UI/menu/crafting/operator-network regressions pass; the production build succeeds; and the Android debug APK passes touch/controller navigation and requirement-state smoke checks.
